### 2.2 首条提交的披露

`b186c7d`（2026-09-04）提交信息为「趣渔 v8.1.0 修复版全量源码」，253 个文件、36,959 行。它**不是**项目从零开始的第一条提交，而是项目在 v8.1.0 时迁入本仓库的基线：v1–v8.0 的开发发生在这个仓库之外，原始逐日历史没有保存下来。

我们**没有**为了满足字面要求去拆分、改时间或伪造这段基线——那会让评审看到一段不存在的历史。可核验的事实是：

- 基线之后的 104 条功能提交（截至 2026-10-11），每条都对应一个明确的功能、修复、门禁或文档模块；比赛文档提交追加在 `5d6940a` 之后；
- 批量提交（如 `b30489d` 清理 45 个死依赖、`265ec41` 76 张图转 WebP、`689f0f7` framer-motion 按需化）是**单一重构动作**，不是把多个功能打包；
- 大版本的功能落地按「DB → API → 前端 → 文档」拆分，例如 v14 的 `a8be879` / `ef184cb` / `a3b9ea7` / `89d77b0`。

评审若把「禁止 initial commit 包含全部功能」理解为「首条提交不得大于某个阈值」，本项目不满足该字面解释；我们选择披露而不是掩盖。

### 3.3 导出方法与一个日志陷阱

Qoder 会把每次会话写成 JSONL：用户真实输入在 `humanInput` 字段，系统注入（goal、skill、工具结果）带 `isMeta` 标记。本次导出用脚本按 `humanInput` 抽取用户轮次，再按时间合并 AI 回复与工具动作。

陷阱：`AskUserQuestion` 的**工具入参**里也带一个 `answers` 字段，但它在多选题、改选、超时场景下可能是旧值。例如 v14「范围边界」的入参写着「只做 B 类」，紧随其后的工具结果却写着「A + B 全做」；「图片存储」入参写着「只做传输瘦身」，工具结果是「插入图片落盘修复」。本文档一律以工具结果中的 `Your questions have been answered: … = …` 为准，并在涉及处标注。这也是一条可复用的结论：**日志里的字段不都是事实，要区分“用户说过”与“界面回填过”。**

1. **远端历史与可见性已于 2026-10-19 处理完毕。** `--force-with-lease` 推送成功，仓库已公开；匿名 API、raw README 与 PDF 均返回 200。执行与回退方式仍保留在 `RELEASE-CHECKLIST.md`。

3. **早期 v8 迭代没有 Prompt 快照。** 本快照覆盖 4 个核心迭代，满足“至少 3 个”，但不覆盖全部 105 条提交。
4. **原始 JSONL 不随仓库分发**，只提供哈希与逐字摘录；如需原始文件，可按 §3.2 校验后单独提供。
5. **生产功能缺口**：识鱼缺 Key、机审未开、支付为测试环境（无商户资质）。这些不影响代码评审，但影响“线上可用”的陈述，故单列。
